# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal
The goal of this sprint is to build the Requester-facing application using a temporary Development Requester identity to simulate multi-user ownership[cite: 8]. By the end of this sprint, a Requester must be able to create an IT support ticket, upload permitted attachments, receive a unique Ticket Number, and manage their own tickets[cite: 8].

## 2. Stakeholder Request Interpretation
The IT department needs a professional and responsive ticketing experience for end users (Requesters)[cite: 8]. Requesters must be able to describe their problems, select categories, attach evidence, and track their issues in a "My Tickets" view[cite: 8]. The system must safely store data, generate official Ticket Numbers, and prevent users from viewing tickets they do not own[cite: 8]. A temporary Development Requester Selection screen will serve as a mock login for testing purposes[cite: 8].

## 3. Scope
### Included
*   Development Requester Selection behavior (testing mechanism)[cite: 8].
*   Create Ticket, My Tickets, and Requester Ticket Detail workflows[cite: 8].
*   Search, filtering, sorting, and pagination for ticket lists[cite: 8].
*   Attachment lifecycle (upload, download, soft-removal)[cite: 8].
*   Zen Green Theme UI specification and responsive behavior[cite: 8].

### Excluded
*   Authentication and security (real login, passwords, tokens, role-based authorization)[cite: 8].
*   IT Staff workflow (dashboards, ticket claiming, changing IT Priority)[cite: 8].
*   Ticket collaboration (Public Comments, Internal Notes, Actions Taken)[cite: 8].
*   Ticket lifecycle after creation (resolving, closing, reopening)[cite: 8].
*   Administration functions (managing users or reference data)[cite: 8].

## 4. Functional Requirements
*   **FR-01:** The system shall provide a Development Requester selector to establish the current testing context[cite: 8].
*   **FR-02:** The system shall allow the Requester to submit a ticket with a Summary, Description, Category, Related System, and Requested Priority[cite: 8].
*   **FR-03:** The system shall provide a paginated, sortable, and filterable My Tickets list restricted to the selected Requester's owned tickets[cite: 8].
*   **FR-04:** The system shall allow the Requester to view their Ticket Detail and add permitted attachments[cite: 8].
*   **FR-05:** The system shall allow the Requester to soft-remove attachments by providing a removal reason[cite: 8].

## 5. Business Rules
*   **BR-01:** The official Ticket Number is generated by the backend and must be unique[cite: 8].
*   **BR-02:** A new Ticket begins with Current Status New[cite: 8].
*   **BR-03:** Lab 2 uses a Development Requester selector instead of login[cite: 8]. The selected identity is for testing only and is not authentication[cite: 8].
*   **BR-04:** Allowed attachment types are limited to JPG/JPEG, PNG, WEBP, and PDF[cite: 8]. The maximum size is 5 MB per file, and a maximum of 5 active attachments are allowed per Ticket[cite: 8].
*   **BR-05:** Attachment removal must be implemented as soft removal[cite: 8]. Removed files must not be downloadable or previewed[cite: 8].
*   **BR-06:** A Requester can only view, manage, or retrieve tickets and attachments that they explicitly own[cite: 8].

## 6. UI Specification Summary
The UI will follow the Zen Green Theme (#006B3C primary, #0B7A46 secondary, #EAF6EF pale green) with a clean white surface and a quiet near-white background[cite: 8]. Required fields will show a red asterisk, and validation messages will appear immediately below the field[cite: 8]. The layout must adapt responsively across Desktop (≥ 992 px), Tablet (768-991 px), and Mobile (< 768 px) viewports without horizontal scrolling or clipping[cite: 8]. 

## 7. Data Changes
The PostgreSQL database (via Prisma) will include models for `DevelopmentRequester`, `Ticket`, `Attachment`, `Category`, and `RelatedSystem`[cite: 8]. The seed data will contain 4 active Development Requesters, 1 inactive Development Requester, the 4 required Ticket Categories, and at least 6 realistic Related Systems[cite: 8]. 

## 8. API Contract Summary
*   `GET /api/requesters`: Retrieve active Development Requesters[cite: 8].
*   `POST /api/tickets`: Create a validated Ticket for the selected Requester[cite: 8].
*   `GET /api/tickets`: Retrieve the selected Requester's tickets with search, filtering, sorting, and pagination metadata[cite: 8].
*   `GET /api/tickets/:id`: Retrieve one owned Ticket Detail[cite: 8].
*   `POST /api/tickets/:id/attachments`: Upload an attachment[cite: 8].
*   `DELETE /api/tickets/:id/attachments/:attachmentId`: Soft-remove an attachment[cite: 8].

## 9. Acceptance Criteria
*   **AC-01:** Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and the official Ticket Number is displayed[cite: 8].
*   **AC-02:** Given no Development Requester is selected, when the user attempts to open My Tickets, then the Requester Selection screen is shown[cite: 8].
*   **AC-03:** Given Requester B is selected, when a Ticket belonging to Requester A is requested, then the Ticket data is not returned[cite: 8].
*   **AC-04:** Given a file upload attempt, when the file size exceeds 5 MB or is an unsupported type, then the upload is rejected with a validation error[cite: 8].
*   **AC-05:** Given an active attachment, when a Requester soft-removes it, then they must provide a reason, and the removed file remains visible as metadata but cannot be downloaded[cite: 8].

## 10. Definition of Done
*   All required tests pass from documented commands in the final main branch[cite: 8].
*   Every acceptance criterion is linked to appropriate test evidence[cite: 8].
*   No required test is skipped, disabled, or commented out[cite: 8].
*   The implemented screens and APIs conform to the approved engineering contract and Zen Green UI specification[cite: 8].
*   README setup and test instructions are current[cite: 8].
